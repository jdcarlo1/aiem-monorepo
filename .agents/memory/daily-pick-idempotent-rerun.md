---
name: Daily-pick-table idempotent rerun pattern
description: How to make a "save today's N picks" write path safe against reruns (admin-triggered + scheduled) without exceeding a per-day cap or corrupting multi-row entities like option contracts.
---

## The problem

A save function that caps picks per call (e.g. `[:20]`) and upserts via
`ON CONFLICT (date, type, ticker) DO UPDATE` looks safe in a single run, but
is NOT safe against reruns: if the same job is triggered twice in one day
(manual admin retrigger + the scheduled run, or a scheduler retry after a
transient failure), each run's rows accumulate on top of the previous run's
rows unless the conflict key happens to force an exact match. Two runs with
even slightly different picks can push the day's total past the intended cap.

A second, related failure mode: if the natural entity key is coarser than
the real-world entity (e.g. keying only on the underlying ticker for an
options table where each row should represent one *contract* — a specific
strike+expiry), the upsert silently collapses multiple legitimate picks
(different contracts on the same underlying) into a single overwritten row.

## The fix

Treat every save call as a full replacement of "today's list for this
type," not an incremental upsert:

```sql
DELETE FROM picks_table WHERE pick_date = %s AND pick_type = %s;
-- then plain INSERT (no ON CONFLICT) for each of today's picks
```

This is wrapped in one transaction with the deletes+inserts, so:
- A rerun the same day always produces exactly the latest run's list, never
  a superset — the per-day cap is guaranteed to hold regardless of how many
  times the job fires.
- No unique constraint is needed on the natural (possibly weak) key, so
  multi-row entities (e.g. several option contracts on one underlying) are
  free to coexist as distinct rows in the same replace batch.

**Why:** discovered via architect review of the Workstream D
`aiem_independent_picks` table (an AIEM-only daily stock+call-option pick
feed, separate from website-derived scores) — the original implementation
used `UNIQUE(pick_date, pick_type, ticker)` + `ON CONFLICT DO UPDATE`, which
both allowed unbounded accumulation across reruns and silently overwrote
option contracts sharing an underlying ticker.

**How to apply:** any "AI saves up to N picks/day" or "daily snapshot" table
that can be regenerated by more than one trigger path (cron job + admin
on-demand endpoint, or automatic retries) should use this delete-then-insert
per (date, type) pattern instead of a upsert-by-natural-key pattern.
