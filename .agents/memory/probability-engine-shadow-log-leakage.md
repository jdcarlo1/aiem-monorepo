---
name: Probability engine shadow-log point-in-time leakage
description: aiem_probability_engine's PIT leakage bug was structurally fixed 2026-07-02; both prior verification gaps (blended track-record endpoint, mislabeled pit_safe rows) closed 2026-07-03 with DB-level proof.
---

ORIGINAL BUG (found 2026-07-02 audit): `reports.generate_and_log_predictions()` used to score any unlogged backlog row with whatever `model_horizon_{h}d.pkl` was currently on disk, regardless of the row's `signal_date` age — 213/225 rows were scored by a model trained on data from after that row's own date.

FIX (2026-07-02, verified independently twice): `model_registry.py` versions every trained artifact by `cutoff_date` + a conservative `label_settled_through` date; `get_as_of(horizon, as_of_date)` requires `label_settled_through` STRICTLY `<` `as_of_date` and returns None (never a fallback) if nothing qualifies; `predict.load_models_as_of()` + `reports.generate_and_log_predictions()` route ALL new scoring through it. `pit_correction.py` does a one-time embargoed re-score of leaked rows into a separate table (`aiem_probability_engine_pit_corrections`), never overwriting the original log.

**Corrected-vs-leaked reality check:** on fully-`corrected` rows, honest PIT-safe AUC is ~0.35–0.53 (roughly coin-flip) vs the leaked models' fabricated 0.94–0.98 AUC on the identical rows. A meaningful fraction of rows are `uncorrectable` (too little embargoed history to train anything) — for those, no honest number exists at all, only the leaked one.

**GAP 1 RESOLVED 2026-07-03 — blended track-record endpoint:** `/stock-api/aiem-probability-engine/track-record` in `main.py` used a single blended AVG/COUNT over all 225 rows (leaked + safe), hiding the leak behind one number. Rewritten to report 3 explicit buckets — `contaminated` (leaked, original inflated scores), `corrected` (embargo-retrained honest scores), `genuine` (post-fix pit_safe, never contaminated) — plus `pit_status` per row. Before/after curl captured: blended number showed a fake 87–92% accuracy; split view shows contaminated 87–92% (labeled untrustworthy) vs corrected 41–54% (honest) vs genuine (0 graded so far, correctly).

**GAP 2 RESOLVED 2026-07-03 — mislabeled pit_safe rows, root cause found and fixed with proof:**
- Root cause: `reports.ensure_table()`'s one-time migration used the heuristic `created_at::date <= signal_date → 'pit_safe' ELSE 'leaked'` for any row with `pit_status IS NULL`. This is a false equivalence — "logged same-day" does not imply "scored via `load_models_as_of()`/registry-gated." 12 rows had `signal_date == created_at::date` purely by coincidence and got mislabeled `pit_safe` despite being scored by the same unversioned, pre-fix `load_models()` pass as 184 rows correctly labeled `leaked`.
- Proof (not inference): all 196 rows sharing `model_version=a6b025e24a5b` were logged in one continuous run (2026-07-01 21:31:30–22:07:33 UTC); the exact boundary between `leaked` and `pit_safe` rows shows the SAME microsecond `created_at` timestamp (22:06:09.604110 UTC) and SAME `model_version` on both sides — e.g. `DDOG`/`2026-06-28` (leaked) and `DDOG`/`2026-07-01` (pit_safe) were inserted in the same transaction instant. `compute_model_version()` on the current (post-fix, 2026-07-02 00:56 UTC-trained) unversioned model files no longer reproduces `a6b025e24a5b` — those files were overwritten by the real fix's training run — confirming `a6b025e24a5b` only ever existed pre-fix.
- Fix applied: (1) DB — the 12 rows were UPDATEd from `pit_safe` to `leaked` via a query scoped exactly to "pit_safe rows whose model_version also appears among leaked rows" (verified 12 rows matched, 12 updated); `pit_correction.py` was re-run and successfully embargo-corrected all 12. (2) Code — `reports.ensure_table()`'s migration heuristic was rewritten to mark ALL pre-existing NULL-`pit_status` rows as `leaked` unconditionally (no same-day carve-out), since only rows stamped `pit_safe` at insert time by the real registry-gated path can be trusted.
- Verified end-to-end: live `/track-record` endpoint now returns `pit_status_counts: {"leaked": 225}` — zero `pit_safe` rows remain until new post-fix rows settle and earn that label honestly.

**Verification technique worth reusing:** when a fix claims "row X was produced by process Y," cross-check `created_at` epoch on the DB row against `mtime`/`trained_at` epoch on the artifact Y claims to have used, and look for exact-timestamp/model_version collisions across rows with different labels — an identical microsecond timestamp on both sides of a label boundary is near-definitive proof the label (not the underlying data) is what's wrong.

**Frontend consumer regression caught same-day (2026-07-03):** changing `/track-record`'s `summary` shape from `{1d:{...}}` to `{contaminated:{1d:{...}},corrected:{...},genuine:{...}}` silently broke `stock-scanner/src/pages/Dashboard.tsx`'s "papermoney" tab (it read `summary?.[h]` directly → always `undefined` → showed "—" with no error). Any time an endpoint's response shape changes, grep the frontend (`api.ts` fetch wrapper + the page that calls it) for that field name before calling the backend change done — `tsc --noEmit` catches type-level breaks but not resilient-looking `?.` chains that just silently render blank.
