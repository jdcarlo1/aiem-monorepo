---
name: Probability engine shadow-log point-in-time leakage
description: aiem_probability_engine's PIT leakage bug (213/225 rows) was structurally fixed 2026-07-02 via model_registry.py, but two verification gaps remain open.
---

ORIGINAL BUG (found 2026-07-02 audit): `reports.generate_and_log_predictions()` used to score any unlogged backlog row with whatever `model_horizon_{h}d.pkl` was currently on disk, regardless of the row's `signal_date` age — 213/225 rows were scored by a model trained on data from after that row's own date.

FIX (same day, verified independently twice — once by me, once by an architect subagent given no prior context): `model_registry.py` versions every trained artifact by `cutoff_date` + a conservative `label_settled_through` date; `get_as_of(horizon, as_of_date)` requires `label_settled_through` STRICTLY `<` `as_of_date` and returns None (never a fallback) if nothing qualifies; `predict.load_models_as_of()` + `reports.generate_and_log_predictions()` route ALL new scoring through it, skipping (not faking) ineligible dates. New rows get `pit_status='pit_safe'`; the 213 pre-fix rows are `pit_status='leaked'`. `pit_correction.py` does a one-time embargoed re-score of the 213 leaked rows into a separate table (`aiem_probability_engine_pit_corrections`), never overwriting the original log.

**Corrected-vs-leaked reality check (independently reproduced twice):** on the 83 fully-`corrected` rows, honest PIT-safe AUC is 0.38–0.56 (roughly coin-flip) vs the leaked models' fabricated 0.93–0.98 AUC on the identical rows. 87/213 rows are `uncorrectable` (too little embargoed history to train anything) — for those, **no honest number exists at all**, only the leaked one.

**Two gaps still open as of 2026-07-02, both disclosed to the user, neither silently glossed over:**
1. `/stock-api/aiem-probability-engine/track-record` in `main.py` (~line 33303) has NOT been updated — its summary-accuracy SQL has no `pit_status` filter, so it still aggregates over all 225 rows including the 213 leaked ones. Fix = add `WHERE pit_status='pit_safe'` (or a per-bucket breakdown) to both the summary query and the row list, and correct the docstring's false "every row logged before its outcome was known" claim.
2. The 12 `pit_safe` rows (signal_date=2026-07-01, model_version=`a6b025e24a5b`) have an unresolved timestamp contradiction: their DB `created_at` (2026-07-01 22:06 UTC) is ~2h50m BEFORE the model files on disk that the current registry says produced that model_version hash (created 2026-07-02 00:56 UTC, confirmed via file mtime + git log showing only one commit ever touched `registry.json`). Running `get_as_of()` for every horizon against `as_of_date=2026-07-01` under the CURRENT registry returns `None` for all 4 horizons — meaning under today's registry state, these rows shouldn't be scorable at all, yet they exist with real probabilities. Root cause not found: `registry.json` is overwritten in place (not append-only), so there's no way to recover what it looked like at the moment these rows were logged. Flag this before treating the 12 "pit_safe" rows as a trustworthy clean baseline — verify it doesn't recur on the next batch of pit_safe rows once some of them settle.

**Verification technique worth reusing:** when a fix claims "row X was produced by process Y," cross-check `created_at` epoch on the DB row against `mtime`/`trained_at` epoch on the artifact Y claims to have used, plus `git log -- <artifact>` to see how many times it's actually been regenerated. A contradiction here is a strong, cheap signal of an undocumented second code path or a broken audit trail — much cheaper than re-deriving the whole pipeline from scratch.
