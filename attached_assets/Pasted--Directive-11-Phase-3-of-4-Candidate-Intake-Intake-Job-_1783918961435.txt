## Purpose
Phase 1 built the schema. Phase 2 enforced the write contract. Phase 3 builds the actual connective mechanism: a separate, Diagram-1-owned component that polls for pending candidates, atomically claims them, and invokes run_full_cycle() — closing the gap between candidate selection and actual analysis.

## Required design
1. Authoritative mechanism = durable DB-backed polling/pull by Diagram 1. This is the source of truth. Do NOT build this as event-driven only.
2. Build a SEPARATE component — Diagram1CandidateIntake with an intake_pending_candidates() entry point. This must NOT live inside or be called from _aiem_paper_pick_candidates(). It is owned by Diagram 1 and scheduled/invoked independently.
3. Atomic claiming: use SELECT ... FOR UPDATE SKIP LOCKED (or an equivalent compare-and-swap on the status field) so that two concurrent intake runs can never claim the same candidate. Prove this — a single claim query, not read-then-write.
4. On claim: transition PENDING_FULL_ANALYSIS → CLAIMED_BY_DIAGRAM1 → FULL_ANALYSIS_RUNNING, then invoke run_full_cycle() for that candidate.
5. On completion: transition to FULL_ANALYSIS_COMPLETED or FAILED. On FAILED, transition to RETRY_PENDING with a backoff delay before re-queueing, up to a max retry count, after which transition to QUARANTINED.
6. An optional CANDIDATE_READY event MAY be added as a low-latency accelerator that triggers an out-of-cycle poll — but polling must still run on its own schedule regardless of whether the event fires, since events can be missed on restart. If you don't build this in Phase 3, state that explicitly and confirm polling alone is sufficient for now.
7. Stale claim recovery: if a candidate has been CLAIMED_BY_DIAGRAM1 or FULL_ANALYSIS_RUNNING for longer than a defined timeout (state the value chosen and why), the intake job must detect and recover it (back to RETRY_PENDING or PENDING_FULL_ANALYSIS) rather than leaving it stuck forever.
8. **Idempotency guarantee:** the same candidate_id must never cause run_full_cycle() to execute more than once for the same claim/attempt — including across a process restart, a retry after stale-claim recovery, or a duplicate poll trigger. Implement this with a durable, unique attempt identifier (e.g., a claim/attempt id or idempotency key tied to candidate_id + attempt number, checked/set atomically as part of the same transaction that performs the claim) so that recovering a stale claim or re-running the intake job cannot invoke run_full_cycle() twice for what is logically the same attempt. A new *attempt* (post-retry, after transitioning back to RETRY_PENDING/PENDING_FULL_ANALYSIS) is expected to run again — the guarantee is against duplicate execution for the same attempt, not against legitimate retries.
