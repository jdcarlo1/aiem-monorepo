# Shadow Learning Check — Strict Verification (run early-to-mid August, or once ~30 graded rows exist)

Two things to verify: (1) the mid-session bug fix from the wiring session
didn't break anything, and (2) once shadow mode has real proposal data,
whether it's behaving correctly.

---

## Part 0 — Verify the mid-session fix first [BEHAVIORAL]

During the wiring session, the agent found and fixed a malformed line
(`conn.cursor() as conn.cursor() as cur`) in the GET proposals endpoint,
in the same batch as several other parallel edits. Confirm this didn't
introduce a regression before trusting anything downstream.

**Prompt:**
```
Show me the current, exact code for the GET /stock-api/admin/learning-proposals
endpoint as it exists right now — not a description, the raw current
function body. Confirm the cursor handling is syntactically correct and
matches standard psycopg2 usage (conn.cursor() as cur, not the malformed
double form).
```

**Verify:**
```
Hit GET /stock-api/admin/learning-proposals with a valid admin token and
with an invalid one. Show raw HTTP response codes and bodies for both,
right now, not from the earlier session's cached results.
```
**Pass condition:** 200 with proposal data (or empty list) for valid token, 403 for invalid — fresh results, not reused from before.

---

## Part 1 — Check whether shadow mode has fired yet [RAW CHECK]

**Prompt:**
```
Query aiem_conviction_eval_log: what is the current row count, and how
many are graded (have an outcome, not NULL)? Query aiem_learning_proposals:
how many rows exist total, and what does the most recent one look like —
raw row, not a summary?
```

**Pass condition:** if graded eval-log rows are still under ~30, shadow mode
hasn't fired yet — stop here and check back later, don't proceed to Part 2
against fabricated or absent data.

---

## Part 2 — If shadow mode HAS produced a proposal, verify it properly [FULL]

Only run this section once Part 1 confirms at least one real row exists
in `aiem_learning_proposals` with `promote=False`.

**Step A — Raw inspection [RAW CHECK]:**
```
Show the raw row(s) in aiem_learning_proposals: old weights, proposed new
weights, what graded data (which eval-log rows, date range, n_samples) the
proposal was based on, and the timestamp. Also confirm: were any
"contaminated" or non-genuine rows included in the training basis? They
should not be.
```

**Step B — Confirm live weights are untouched [BEHAVIORAL]:**
```
Print the CURRENT live weights actually used by _run_five_layer_conviction
right now. Compare them to what they were before this proposal was
generated (check git history or the earlier wiring-session logs). Confirm
they are IDENTICAL — the proposal must not have been auto-applied.
```
**Pass condition:** live weights unchanged, proposal exists only as a logged row.

**Step C — Fresh-context adversarial review [FULL]:**
```
[New session, no memory of this task]
Here is a machine-learning weight-update proposal generated by a shadow-mode
gradient descent process, based on graded trading outcome data. Review it
skeptically:

1. Does the proposed weight change make directional sense given the
   training data described? (e.g. if a layer consistently correlated with
   losses, did its weight decrease — or did something backwards happen?)
2. Is there any sign of overfitting to a small sample (30 rows is a small
   n — are the proposed changes drastic relative to that sample size, which
   would be a red flag)?
3. Does the held-out validation split look legitimate (time-ordered, not
   leaking future data into the training portion)?
4. Would you trust this proposal to go live as-is, or does it need more
   data first?

Proposal data:
[paste raw row from Step A]
```

**Step D — Fact-check the adversarial review's claims against raw evidence**
before accepting or dismissing anything it says — same standard as the
earlier conviction-stack wiring review.

**Pass condition for the whole section:** proposal is directionally sensible, not overfit to n=30, uses a legitimate time-ordered split, and — given it's still one proposal off a small sample — the honest answer to "would you trust this live" should probably be "not yet, need more graded cycles" rather than an immediate promotion.

---

## What NOT to do

- Do not approve/promote a proposal (via the gated admin endpoint) based
  on a single shadow-mode cycle. One proposal off ~30 samples is a first
  data point, not a trend. Wait for several cycles before even considering
  the manual-approval step from the original wiring plan.
- Do not skip Part 0. A fix made in the same batch as five other parallel
  edits deserves a fresh look before trusting anything built on top of it.
