## PHASE 1 — FIX THE DECORATIVE `enforcement_status` FIELD

**Problem confirmed:** `enforcement_status = "ENFORCED"` / `enforcement_action = "BLOCKED"` is written at 13 locations but nothing reads it back — the real gate everywhere is `decision.get("...") == "BLOCK"`. The field is cosmetic and misleading to anyone reading the DB later (including future audits).

**Fix — pick one, not both:**

**Option A (recommended): Make the field truthful, not functional.**
Rename it at all 13 write sites to something that can't be mistaken for a live gate, e.g. `enforcement_status_if_enforce_mode` or `simulated_enforcement_status`. Add a one-line comment at each site: `# Descriptive only — does not gate execution. Real gate is decision=="BLOCK" above.` This is the low-risk fix: no behavior change, just stops the field from lying by omission.

**Option B: Make the field real.**
Add an explicit read-back check derived from the same field, e.g.:
```python
if enforcement_status == "ENFORCED" and decision != "BLOCK":
    raise GovernanceInconsistencyError(...)
```
This adds a consistency guard between the status label and the actual decision, so if they ever diverge (a real bug class), it's caught immediately instead of silently drifting. Higher engineering value, but only do this if Phase 0 rollback proof is solid, since it introduces a new failure mode to test.

**Proof required for either option:** grep output showing all 13 sites updated identically, plus one live run showing the new comment/check present and not breaking the existing BLOCK/ALLOW behavior.
