## SEVERITY 1 — Tool map mismatch (this is your real "complicated questions"
## problem — not a shortage of tools)

**Location:** `_run_aiem_focused_session()`, the `_fs_tool_map` dict
(~line 22954–23027 in the reviewed export).

**What's wrong:** This function is what currently answers SMS/email "ask
AIEM" questions, and would power a future chat tab. It uses `_fs_tool_map`,
a 64-entry dict. But the tool *schema* you hand to gpt-4o
(`_AIEM_AGENT_TOOLS`, shared across your whole app) advertises 83 tools.

**34 of those 83 advertised tools have NO entry in `_fs_tool_map`.** Every
time the model reaches for one of these on a complex question, it gets
`{"error": "unknown tool: X"}` back and burns an iteration for nothing:

```
mkt_generate_hypotheses, mkt_discover_interactions, mkt_test_inverse,
mkt_check_survivorship, mkt_required_pvalue, mkt_segment_by_sector,
mkt_volatility_squeeze, mkt_accumulation_squeeze, mkt_extreme_move_reversion,
mkt_gap_fill_probability, mkt_refresh_universe, mkt_signal_drift,
mkt_invent_indicator, mkt_compare_signals, mkt_check_redundancy,
mkt_analyze_false_signals, query_market_regime, query_missed_movers,
query_temporal_patterns, query_rank_effectiveness, query_exit_timing,
query_own_prediction_performance, query_cross_signal_overlap,
analyze_signal_correlation, compare_picks_vs_misses,
discover_numeric_patterns, evaluate_previous_model,
rollback_to_previous_model, holding_period_optimize, kelly_position_size,
list_signal_dimensions, multivariate_regression, register_hypotheses,
signal_layer_redundancy, signal_magnitude_analysis, test_scoring_hypothesis
```

These are exactly the deep statistical/research tools a *complicated*
question needs — so complex questions are disproportionately the ones that
hit this bug.

There's a smaller reverse problem too: 17 tools are wired into
`_fs_tool_map` but missing from the schema, so the model never knows it
can call them (`send_discovery_alert`, `run_risk_gate`, `breakout_discover`,
`divergence_scan`, `check_price_bullish`, `regime_overlay_check`,
`regime_overlay_manual`, `retrain_pending/approve/reject/history`,
`gate_history`, `squeeze_subscore`, `gap_continuation_score`,
`intraday_continuation_score`, `intraday_compute_features`,
`breakout_extract_features`).

**Why this matters:** your *other* agent loop, `_run_aiem_research_agent`
(the main 24/7 overnight loop, ~line 26915), already has a correct, far more
complete map called `_tool_map` (~line 26959–27101, 130+ entries) wired to
the exact same `_AIEM_AGENT_TOOLS` schema. The fix isn't building new
tools — it's pointing `_fs_tool_map` at the same map `_tool_map` already
uses. I merged the two maps (deduped, no conflicting function references
found between them) — see `main_py_patches.py`, section 1.

**Fix:** Replace the `_fs_tool_map` dict in `_run_aiem_focused_session`
with the merged map in `main_py_patches.py` section 1.

## SEVERITY 2 — Raw OpenAI message object appended to `messages` list

**Location:** `_run_aiem_focused_session()`, line ~23054: `messages.append(msg)`

**What's wrong:** `msg` is the SDK's message object, not a plain dict. On
some openai-python versions re-serializing this on the next API call either
throws or silently drops `tool_calls` fields. Your existing per-iteration
try/except (line 23073) catches the resulting crash and just `break`s, so
the session ends early and silently returns whatever partial text it has —
which looks like a complete answer but isn't. This is very likely
contributing to "thin" answers on multi-step questions, separately from the
tool map bug above.

**Fix:** Convert to a plain dict before appending. See
`main_py_patches.py` section 2.

## SEVERITY 3 — SMS webhook bypasses your own concurrency lock

**Location:** `/sms/incoming` Twilio webhook handler, ~line 40874–40906.

**What's wrong:** Your email-based "ask AIEM" path (~line 9817-9833)
correctly acquires `app._aiem_qa_lock` (a `Semaphore(1)`, initialized at
line 9686) before starting a session, so only one Q&A session runs at a
time. The SMS webhook handler starts a session the same way but **never
acquires that lock** — so a text message can launch an AIEM session
concurrently with a scheduled cron session, an email-triggered session, or
another text. Beyond wasted GPT-4o spend, this is a real correctness bug:
the SMS handler then does

```sql
SELECT insight_text FROM aiem_research_insights ORDER BY created_at DESC LIMIT 1
```

to fetch "the" answer — if two sessions finish close together, the SMS
reply can read back a different session's answer than the one it asked for.

**Fix:** Acquire the same `app._aiem_qa_lock` in the SMS handler, and tag
the insight row with the session_name so the read-back can't cross-talk.
See `main_py_patches.py` section 3.
