## 12. n=337 backtest — bucket_id / "non-overlapping" claim doesn't hold up

The n=337 backtest query uses `bucket_id = (rn-1)/1` where `rn` comes from `ROW_NUMBER() OVER (PARTITION BY ticker ORDER BY scan_date)`. With a bucket size of 1, `rn` is already unique per (ticker, date) — so `bucket_id` is too. That means the following `DISTINCT ON (ticker, bucket_id)` dedup step removes nothing, because there's nothing to deduplicate. Functionally this query is just a plain per-row scan, identical to not bucketing at all.

This was described as "rigorous non-overlapping LAG-aware testing," which overstates what the query actually does. If the intent was to prevent overlapping multi-day holding periods from double-counting the same move, an H=1 bucket doesn't test that at all — it would need H>1 (a real holding-period window) or explicit exclusion logic to matter.
