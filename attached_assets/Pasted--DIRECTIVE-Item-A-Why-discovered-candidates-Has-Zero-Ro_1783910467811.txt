# DIRECTIVE — Item A: Why `discovered_candidates` Has Zero Rows Ever

## Background / Why This Directive Exists

Confirmed via raw SQL in prior sessions:
- `daily_market_movers` is active and healthy: 800 rows/day (100 winners + 100 losers × 4 market-cap tiers), latest scan date 2026-07-10.
- `run_tiered_wl_cycle()` reads from `daily_market_movers`, computes IS/OOS win-rate statistics per `_WL_HYPOTHESIS_TEMPLATES`, and calls `_save_candidate()` for each template — which is supposed to write to the `discovered_candidates` table.
- `discovered_candidates` has **0 rows, ever** — despite this cycle running daily on 800 fresh rows of labeled data.

This means either:
(a) The win-rate/OOS filter is legitimately strict and correctly rejecting every single candidate every day (working as intended, just conservative), or
(b) There is a logic bug in `_save_candidate()` or the threshold comparison that is silently rejecting everything regardless of the actual stats (e.g. wrong comparison operator, wrong column reference, inverted condition, unit mismatch).

This directive exists to determine which of these two is true, with evidence — not to fix anything yet.

## Task

- The exact comparison operators used (`>`, `>=`, `<`, `<=`, `==`).

### Step 2 — Run `run_tiered_wl_cycle()` (or extract its most recent real output) and capture the actual computed stats

For the most recent real run (or by re-running it if safe to do so — confirm with Joel first if this would write any new data, per the Data Immutability rule below), capture:
- The actual win-rate/OOS numbers computed per tier/template.
- The `proposed`, `rejected`, `by_tier`, and `oos_cutoff` values from the returned summary dict.
- Paste this raw, not paraphrased.

### Step 3 — Compare Step 1's threshold logic against Step 2's actual numbers

For at least 3 rejected candidates (or all of them if there are few), show the actual computed win-rate/OOS value next to the threshold it was compared against, and state explicitly whether the rejection is:
- **Correct** — the candidate genuinely failed the stated threshold, or
- **A bug** — the candidate should have passed by the stated threshold's own logic, but got rejected anyway (e.g. due to a wrong operator, wrong variable reference, or a comparison against the wrong column).

### Step 4 — Direct answer

State explicitly: **Is the zero-candidate result a legitimately strict filter working as intended, or a logic bug silently rejecting everything?**

If a bug is found, identify the exact line and the exact nature of the bug (do not fix it yet — this directive is diagnostic only, unless Joel has separately authorized a fix in the same message).
