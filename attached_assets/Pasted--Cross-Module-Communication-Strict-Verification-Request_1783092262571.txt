# Cross-Module Communication — Strict Verification Requests

**Purpose:** The Phase 1 report proves individual modules work correctly in isolation. It does not yet prove the modules are reliably *reaching* each other under real conditions. This file is the follow-up ask — same "prove it, don't tell me" standard: raw terminal output, SQL query results, or timestamped log rows only. No self-report ("it's wired," "it's working") accepted as a verification.

---

## 1. Structural Reachability — Code Calling Code vs. Agent Choosing To

**Ask:** For every gate in the safety pipeline (kill_switch, simulation_lock, pre_decision_risk_gate, daily_loss_limit, order_dedup, earnings_calendar, portfolio_correlation_risk, position_reconciler) — provide the exact call site showing whether it is:

- **(a)** an unconditional function call inside `evaluate_ticker()` or the scheduled execution path, or
- **(b)** a tool the AIEM agent is only instructed, via system prompt, to call

**Proof required:** File + line number of the call site, plus a one-line note: "unconditional" or "agent-discretionary." No summary language — just the call chain.

**Why:** (a) means the check cannot be skipped. (b) means it can, if the agent doesn't run, crashes, or skips the tool call. This is the single most important distinction in the whole system.

---

## 2. Fail-Closed vs. Fail-Open Under Missing Dependencies

**Ask:** Run each gate with a required dependency deliberately removed, and report what happens:

- Risk gate with `ANTHROPIC_API_KEY` unset — does it hard-block a weak signal (WR=30%, n=10, conviction=0.2), or does it downgrade to `APPROVED_WITH_CAUTION`?
- Any DB-dependent gate with `AIEM_DATABASE_URL`/`DATABASE_URL` unreachable — does the system halt, or proceed silently?
- Kill switch with the DB connection dropped mid-check — does trading halt by default, or continue?

**Proof required:** Raw output of each test, run twice — once with the dependency present, once removed — side by side.

**Why:** A system that quietly gets *weaker* when something breaks is worse than one that visibly stops. This is the test that catches silent degradation, which the original audit already flagged as a live risk for the risk gate specifically.

---

## 3. End-to-End Path Test, Not Isolated Function Calls

**Ask:** Instead of calling `check_kill_switch(...)` or `run_risk_gate(...)` directly in a test script, trigger the **actual scheduled premarket run** (or a manual equivalent that goes through the real `evaluate_ticker()` entry point) under conditions that should trip each gate. Then query the database for the resulting row — don't report terminal output alone.

**Proof required:** For each gate, the SQL query and result row from the relevant table (`risk_gate_decisions`, `kill_switch_events`, `daily_loss_breach_log`, `reconciliation_log`) generated by a real end-to-end run, with a timestamp.

**Why:** A function passing in isolation proves the function is correct. It does not prove it's reachable from the real execution path — that's the actual gap flagged in kill_switch and simulation_lock.

---

## 4. Cross-Table Timestamp Ordering

**Ask:** Pull every row from `risk_gate_decisions`, `kill_switch_events`, `daily_loss_breach_log`, and `reconciliation_log` for a single real trading day, alongside the corresponding rows in `ai_stock_picks`. Confirm gate timestamps precede the pick's creation timestamp, not follow it.

**Proof required:** One combined query result (or four queries run together) showing timestamps in order, for at least one real trading day — not a synthetic test day.

**Why:** This is the one piece of evidence that shows the whole pipeline in sequence, rather than trusting six separate module reports to add up correctly. If a gate's timestamp comes *after* the pick was already written, the gate didn't actually block anything.

---

## 5. Negative Tests Under Real Failure Conditions

**Ask:** Every existing test proves "bad signal in → correctly blocked." Provide the missing complement: "dependency removed → still blocks, or silently weakens?" Specifically:

- Missing API key → risk gate behavior (see #2)
- Agent not running at all during the 9:52 AM window → does anything catch that kill_switch/simulation_lock were never checked, or does a pick get written anyway?

**Proof required:** Test run + raw output for each scenario, plus explicit statement of what (if anything) currently detects or alerts on the agent simply not running.

---

## Summary — What to Send Back

> "Before I can call this system fully wired, I need:
> 1. Call-site proof for every gate — unconditional code path or agent-discretionary tool, no exceptions.
> 2. Each gate tested with its dependency removed, to confirm fail-closed behavior.
> 3. At least one gate proven via a real scheduled run + database query, not an isolated function call.
> 4. One day's worth of gate timestamps compared against pick-creation timestamps, in order.
> 5. A test for what happens if the AIEM agent simply doesn't run during the trading window — does anything catch that, or does a pick go through unguarded?"
