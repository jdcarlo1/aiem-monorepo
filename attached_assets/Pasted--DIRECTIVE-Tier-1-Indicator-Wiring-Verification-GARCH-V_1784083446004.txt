## Task

For each of the three Tier 1 indicators — GARCH (volatility clustering/persistence), VPIN (order flow toxicity), Hurst Exponent (trending vs. mean-reverting regime) — confirm:

1. **Where the value is computed** — exact file, function, line range.
2. **The full call chain** from computation to `bull_bear_debate.signal_context`, with every intermediate structure named (e.g., does it pass through `packet.microstructure` first, and if so, is that struct actually read downstream or is it a dead handoff?).
3. **A real live run during market hours** — not backtest, not a stubbed/mock ticker — showing the indicator's actual computed value landing inside `signal_context` at decision time.
4. **Whether `ensemble_combiner` or the decision path downstream actually uses the value**, or whether it's present in `signal_context` but functionally inert (as was found for Thompson Sampling and Bayesian Statistics in the 39-indicator audit — do not assume presence means usage).

Do this per-indicator, not as a combined summary. If any one of the three fails the chain at any point, report that specific failure — do not average status across the tier.

## Negative Control Requirement (applies to every indicator)

Proving the happy path is not sufficient — presence of a value in `signal_context` does not prove the pipeline actually depends on it (a hardcoded or injected constant could satisfy the happy-path check alone). For each indicator, also prove the failure path:

1. State what you are about to disable or corrupt and why, and wait for approval before doing it (same principle as the Data Immutability Rule — no unilateral changes to live code behavior).
2. Disable or corrupt the indicator's value at its source.
3. Show the pipeline detects the missing/corrupted value (raw output, not a description).
4. Prove the downstream decision changes, or that validation fails — either is acceptable, but one of the two must be demonstrated with evidence.
5. Restore the original implementation and confirm restoration with a diff/hash showing it matches pre-test state.

Skipping this leaves open the possibility that a constant value was injected and the happy-path evidence alone would not catch it.

## Provenance ID Requirement (applies to every piece of evidence)

Every piece of raw evidence submitted for this directive — grep output, diffs, SQL results, trace output — must carry consistent identifiers across the full chain, so the evidence is provably one continuous execution rather than stitched together from separate runs:

- `trace_id`
- `candidate_id`
- `decision_id`
- `signal_context_id`
- `indicator_instance_id`

Where a given piece of evidence doesn't naturally carry one of these (e.g. a pure code-location grep), that's fine — but anywhere a live run is being demonstrated (items 2–4 in the Task list, and the negative control above), the same ID set must appear and match across every artifact from that run.

## Standing Verification Block (non-negotiable, applies to every claim below)

No task is complete based on description alone. For every claim of "wired," "confirmed," "reaches," or "used," provide:

1. **Raw terminal output** of actual execution — including raw `grep` output for any claim about code location, call chains, or whether a function/pattern exists. Never paraphrase what grep would show.
2. **Exact before/after file diff** for any file touched.
3. **sha256 hash before/after** for any changed file.
4. **Raw SQL query + full result set** for any database-involved claim (e.g., confirming a row in `aiem_signal_discoveries` or trace tables reflects the live value).

Narrative/paraphrased claims of "fixed," "tested," "found," or "confirmed" without pasted raw evidence are rejected. If evidence cannot be produced, the agent must say so explicitly rather than asserting completion.
