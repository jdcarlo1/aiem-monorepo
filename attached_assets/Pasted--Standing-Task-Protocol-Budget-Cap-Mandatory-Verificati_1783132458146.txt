# Standing Task Protocol — Budget Cap + Mandatory Verification

Paste this at the start of every task given to the agent. It caps runaway cost from over-claiming/rework and forces evidence over narrative on every single response, not just when asked.

---

## 1. Budget cap (state up front, every task)

- **Max iterations for this task: [N]** (default 6 unless task is known to be complex — set explicitly each time)
- **Max session time: [X minutes]**
- If you hit the cap without a verified done state, STOP. Report exactly what state things are in, what's blocking completion, and what you'd need to finish — do not keep iterating silently past the cap.
- Do not restart from scratch on a stall. Report the stall.

## 2. Definition of "done" for this task (state explicitly)

Before starting, write out: what does a raw, checkable artifact of completion look like for this specific task? (e.g. "a passing test output," "a git commit hash," "a specific DB row with a specific value.") If you can't define this before starting, ask before proceeding.

## 3. Every response must include, when claiming progress or completion

- [ ] The raw artifact (terminal output, DB query result, diff, HTTP response, log line) — not a description of it.
- [ ] If a claim can't be backed by a raw artifact yet, say so explicitly: "not yet verified" rather than asserting success.
- [ ] If code review / a reviewer step exists for this platform, its verdict must be shown verbatim, and no "done" claim is valid until that verdict is APPROVED. A rejected or missing verdict = not done, full stop, regardless of what else works.
- [ ] Any new bug found during this task must include: root cause (not just symptom), the diff that fixes it, and before/after evidence — not just "fixed and verified."

## 4. Anti-rationalization checks (self-apply before responding)

- [ ] Am I about to say something is "done," "fixed," "verified," or "confirmed" without pasting the actual raw output?
- [ ] Am I explaining away a failure (mis-scoped, unrelated, cosmetic, edge case) instead of showing why that explanation is true?
- [ ] Have I run this claim against a negative control — i.e., checked a case where it *should* fail, to prove my positive result isn't a coincidence?
- [ ] Am I reporting a summary number (pass rate, count, percentage) without showing the query/log that produced it?

If any answer is "yes, and I haven't backed it up," don't send the claim yet — go get the evidence first.

## 5. Cost/time accounting (report at end of every task)

- Iterations used: [N] / [cap]
- Time used: [X min] / [cap]
- Number of times a claim had to be walked back or re-verified this session: [N]
- If this number is >0, state what caused the false claim and what will prevent it next time — don't just move on.

## 6. Escalation rule

If the same category of issue (e.g. "claimed done, wasn't") happens twice in one task, stop and flag it explicitly rather than trying a third time silently. Ask for direction before continuing to burn iterations on the same failure mode.

---

**Bottom line for the agent:** A shorter response with real evidence beats a longer one with confident claims. If you're not sure, say you're not sure. If you hit the cap, stop and report rather than continuing to work "for free" on an unbounded loop.
