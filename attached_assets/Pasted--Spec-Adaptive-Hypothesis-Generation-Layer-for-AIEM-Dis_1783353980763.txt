## Context

The current Discovery Engine (`aiem_discovery_engine.py`) tests a fixed, human-written set of hypothesis templates (T01–T10) through an IS/OOS backtest, overfit check, sample-size gate, and baseline-edge gate. This works well but requires a person to write every new template by hand.

This spec adds three modules that sit **on top of** the existing evaluation pipeline — `_evaluate()`, `_compute_stats()`, `_check_overfit()`, and the baseline-edge gate must be reused as the fitness function, not rebuilt. The goal is a system that generates its own hypotheses and adapts over time, not one that replaces the verification discipline already in place.

**Explicit non-goal:** none of this authorizes live trading autonomously. Human approval for live/paper execution remains unchanged. These modules only affect what gets *proposed* for review, not what gets *acted on*.

---

## Module 1 — Genetic Programming / Symbolic Regression (hypothesis generation)

**Purpose:** Generate new candidate feature-rule templates automatically instead of requiring a person to write `{"rvol": ("gte", 3.0), ...}` by hand.

**Requirements:**
- Population of candidate rules, each expressed in the same feature-rule dict format the existing templates use (`gap_pct`, `rvol`, `close_strength`, `range_pct`, etc.), so they're compatible with `_evaluate()` unchanged.
- Each generation's candidates must be run through the existing `_evaluate()` pipeline (IS/OOS split, overfit check, sample-size gate, baseline-edge gate) — do not build a separate/simplified scoring function.
- Selection, crossover, and mutation operators clearly defined and logged per generation.
- Hard cap on population size and generations per cycle to bound compute cost — state the proposed caps and the reasoning.
- Suggested library: `gplearn` or `DEAP`. State which was chosen and why.

**Verification required after implementation:**
1. Paste the full generation loop, not a summary.
2. Show one full generation's raw output: population before, fitness scores after, which candidates survived.
3. Confirm every surviving candidate actually passed through the *real* `_evaluate()` function — grep for the call site, not a reimplementation.
4. Show at least one example of a genuinely novel rule combination that a human likely wouldn't have written by hand.

## Module 2 — Contextual Bandit / RL Layer (adaptive real-time weighting)

**Purpose:** Continuously re-weight which surviving rules get attention as new trade outcomes settle, rather than waiting for the next full retrain cycle.

**Requirements:**
- Each surviving rule (from Module 1 or the existing static templates) is treated as an arm.
- Reward signal must be defined explicitly and tied to real settled outcomes (e.g., next-day return), not a proxy that can be gamed by the bandit itself.
- Specify exploration strategy (epsilon-greedy, UCB1, Thompson sampling — pick one and justify) and how it's bounded so exploration doesn't dominate capital allocation.
- Integration point with the RL engine expansion already underway in AIEM — state explicitly whether this becomes a new action space for that engine or a standalone layer, and why.
- Explicit safeguard against reward hacking: state what would prevent the bandit from converging on a rule that scores well against the reward function but has no real economic edge (e.g., periodic re-validation against the baseline-edge gate, not just the bandit's internal reward).

**Verification required after implementation:**
1. Paste the reward function definition in full and confirm it's computed from real settled trade data, not a placeholder.
2. Show the arm-weight history over at least one real time period — which rules gained/lost weight and why.
3. Confirm (via grep or direct trace) that bandit output still passes through human-gated promotion — it does not get to skip `promote_candidate()`'s human-approval requirement.

## Module 3 — Online/Incremental Learning (continuous data adaptation)

**Purpose:** Allow feature statistics (win rates, overfit gaps, baseline comparisons) to update incrementally as new `polygon_market_daily` rows arrive, rather than requiring a full batch retrain to reflect recent data.

**Requirements:**
- Specify what updates incrementally (e.g., rolling baseline_wr) versus what still requires a full batch recompute (e.g., IS/OOS split logic) — not everything can or should be made incremental.
- Suggested library: `river` (Python) for incremental statistics, if applicable.
- Explicit data-quality guard: incremental updates must not silently absorb a bad data row (e.g., a bad print, missing volume) into a moving statistic without some sanity check. State what that check is.

**Verification required after implementation:**
1. Show the exact rolling/incremental computation in full.
2. Compare incremental output against a batch recomputation over the same window — confirm they match within acceptable tolerance, and show the actual numbers, not a claim that they match.
3. Confirm what happens on a bad/missing data row — does it get filtered, flagged, or does it silently corrupt the running statistic? Demonstrate with a real or synthetic bad row.
