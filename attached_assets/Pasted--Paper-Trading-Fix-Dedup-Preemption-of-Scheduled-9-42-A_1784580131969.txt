# Paper Trading — Fix Dedup Preemption of Scheduled 9:42 AM Run

## Priority
This is the top priority — getting daily paper trading to actually execute automatically
every day, not just have its trigger fire.

## The problem (confirmed 2026-07-20)
The 9:42 AM ET CronTrigger has the correct timezone and does fire. But on 2026-07-20 it
produced NO execution because a `startup_recovery` run had already logged a row at 9:00 AM
ET (id=20, status=NO_CANDIDATES, trades_inserted=0). Whatever dedup/ledger check gates the
scheduled run treated "a row already exists for today" as "today is done" and skipped the
9:42 run entirely — even though that earlier row reflected zero candidates checked, not a
real completed attempt.

## Required — investigate first, raw evidence only
1. `grep -n` the dedup/gating logic that decides whether the scheduled 9:42 run proceeds
   (likely near `trigger_source="scheduled_942"` in main.py). Paste the raw grep output
   and the surrounding function in full via `sed -n`.
2. State plainly: what exact condition currently causes a skip? (e.g. "any row exists for
   today" vs "a row with status=SUCCESS exists for today")

## Required fix
The scheduled 9:42 AM run must proceed unless a row for today already shows a REAL
completed execution attempt (i.e. status SUCCESS or FAILED with trades actually attempted/
inserted) — not merely because some earlier process (startup_recovery, internal_watchdog)
logged a placeholder/zero-candidate row. A NO_CANDIDATES row from an earlier check should
never block the scheduled run from actually trying at 9:42.

Decide and state which of these two behaviors you're implementing, then apply it:
- (a) scheduled run always executes at 9:42 regardless of any earlier row today, and the
  ledger just records both entries, or
- (b) scheduled run executes unless today's existing row has status SUCCESS or a real
  FAILED-after-attempt state (NO_CANDIDATES does not count as "already handled")
