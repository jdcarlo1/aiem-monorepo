============================================================
AEIM ADVANCED QUANTITATIVE INDICATOR
AUTHORITATIVE WIRING, REMEDIATION, AND LIVE VERIFICATION

PURPOSE

Audit, remediate, and prove the production wiring of every advanced
quantitative indicator in AEIM Diagram 2.

This is not a narrative review.

This is not permission to create fake modules, placeholder functions,
mock calculations, synthetic traces, hard-coded outputs, or alternate
architecture merely to obtain a PASS result.

The objective is to establish, with real code and real runtime evidence,
that every advanced quantitative indicator:

1. Exists in the production codebase.
2. Has one canonical implementation.
3. Has one canonical architectural owner.
4. Is registered in the authoritative Module Registry or Tool Registry.
5. Initializes successfully.
6. Receives authorized upstream inputs.
7. Executes real quantitative logic.
8. Produces a structured output.
9. Has its output consumed by an authorized downstream component.
10. Contributes only where architecturally authorized.
11. Cannot directly bypass synthesis, governance, or risk controls.
12. Produces traceable provenance and runtime evidence.
13. Runs at the correct cadence.
14. Fails closed when required data or dependencies are unavailable.
15. Is protected against fabricated success and silent fallback.

Do not return a generalized statement that the indicators are wired.

Each named indicator must receive an individual evidence record.

============================================================
SECTION 1 — NON-NEGOTIABLE ARCHITECTURAL FLOW

The canonical Diagram 2 flow is:

AEIM Self-Scan / Authorized Candidate Intake
→ Point-in-Time and Data Quality Guards
→ Macro and Market Regime Context
→ Discovery and Hypothesis Selection
→ Technical, Options, Microstructure, and Quantitative Analysis
→ Probability Engine
→ Scoring and Pre-Recommendation Synthesis
→ Specialist Council
→ Pre-Decision Risk Gate
→ G2 Governance Check
→ Decision Engine
→ Paper/Shadow Execution or Authorized No-Execution Record
→ Outcome Tracking and Attribution
→ Safe Learning
→ Memory
→ Feedback to Master Orchestrator

No advanced quantitative indicator may communicate directly with:

1. The Decision Engine.
2. The execution layer.
3. The broker adapter.
4. Telegram alert dispatch.
5. Position creation.
6. Order creation.
7. Diagram 3 governance mutation controls.

Indicators provide evidence.

They do not independently authorize trades.

============================================================
SECTION 2 — CANONICAL OWNERSHIP RULES

Each indicator must have exactly one canonical owner.

Permitted owners include:

A. Data Guard Layer
B. Macro/Regime Layer
C. Discovery/Hypothesis Layer
D. Technical Analysis Layer
E. Options/Microstructure Layer
F. Quantitative/Statistical Edge Layer
G. Probability Engine
H. Scoring/Synthesis Layer
I. Learning and Signal-Lifecycle Layer

A second implementation may exist only when explicitly classified as:

1. A versioned replacement awaiting approval.
2. A test-only implementation.
3. A research-only implementation.
4. A deprecated implementation that cannot execute in production.

Two active production implementations of the same indicator are prohibited.

10. Add or update tests.

existing authorized classification.
