## 3. Behavioral proof — force each gate to fire and capture raw output

Do NOT accept "I tested it and it works." Require the actual printed/logged output for each of these 4 forced scenarios.

### A. Daily loss limit

```bash
DAILY_LOSS_LIMIT_PCT=0.01 python3 -c "
import premarket_open_trader as pot
import os
print(pot.evaluate_ticker(os.environ['DATABASE_URL'], 'AAPL', premarket_gap_pct=4.5))
"
```

- **Pass condition:** output shows `decision: skip` (or equivalent) and the blocker text contains "daily loss limit breached". Confirm no new row was written to `ai_stock_picks` for this run:

```sql
SELECT * FROM ai_stock_picks WHERE ticker='AAPL' AND pick_date=CURRENT_DATE;
```

### B. Position mismatch

Temporarily edit `position_reconciler.mock_position_source()` to return a ticker not in the DB (e.g. add `{"ticker": "ZZZZ", "qty": 5, "side": "long"}`), then rerun `evaluate_ticker()`.

- **Pass condition:** blocker text contains "unresolved position mismatch"; `reconciliation_log` gets a new row with `mismatch_found = true`. Revert the mock edit after.

### C. Portfolio correlation risk

Manually insert 3+ open positions from the same `CORRELATION_GROUPS` bucket in `portfolio_correlation_risk.py` (e.g. 3 of AAPL/MSFT/GOOGL/NVDA) into `ai_stock_picks` with `status='open'`, then rerun `evaluate_ticker()` for a 4th correlated ticker.

- **Pass condition:** blocker text contains "concentration risk"; decision is `skip`.

### D. Order dedup

Call `evaluate_ticker()` twice in immediate succession for the same ticker on the same day where decision would be `enter_now`.

- **Pass condition:** both counts must be exactly 1, not 2. If either is 2, dedup is not actually blocking the second write — the `should_place_order()` check is either not being called or not gating the write.

## 5. Regression check — make sure gating a legitimate trade wasn't broken

Run `evaluate_ticker()` for a ticker/scenario where all 4 gates should pass clean (no loss breach, no mismatch, no concentration, no existing decision_id) and confirm:

```sql
SELECT COUNT(*) FROM ai_stock_picks WHERE ticker='<TICKER>' AND pick_date=CURRENT_DATE;
SELECT COUNT(*) FROM order_execution_log WHERE ticker='<TICKER>' AND submitted_at::date=CURRENT_DATE;
```

Confirm:
- Decision can still reach `enter_now`
- A row is written to `ai_stock_picks`
- A row is written to `order_execution_log`

- **Pass condition:** a healthy trade still goes through. If the new gates are wired so strictly that nothing can ever pass, that's a false-positive bug, not a working safety system.
