## 1. NON-NEGOTIABLE STANDARD

For every factual claim about code, the agent must supply **all four** of the following, or the claim is rejected outright:

1. **File path** (absolute or repo-relative, exact)
2. **Line number(s)** cited
3. **A `sha256` hash of the exact file being cited**, generated at the moment of the claim, via:
   ```
   sha256sum <filepath>
   ```
4. **The literal, unmodified line content** at that line number, via:
   ```
   sed -n '<line_start>,<line_end>p' <filepath>
   ```

You (Joel) independently re-run steps 3 and 4 yourself, in your own terminal, against your own copy of the repo. If the hash or line content the agent reports does not match what you get, the claim is fabricated — full stop, no benefit of the doubt.

**Do not accept a paraphrase, screenshot description, or "I checked and it's there" as a substitute for raw command output.**

## 2. THE FOUR CONTRADICTED CLAIMS — REQUIRED PROOF FOR EACH

### Claim A — G0 return path is real
**Agent's claim:** `require_governance_authorization` in `_aiem_paper_execute_today` (line 42724) calls `_AIEM_PAPER_LOCK.release(); return` on a BLOCK decision, and this stops D2 execution.

**Required proof:**

- `sed -n` output of lines 42700–42740 (context window around the cited line), not just the single line.
- Confirmation of **every other call site** that reaches order execution — grep for all callers of the execution function, e.g.:
  ```
  grep -n "_aiem_paper_execute_today\|execute_stage" *.py
  ```
  The original contract found 5 of 6 `execute_stage()` call sites bypassing G0 entirely. This must be re-checked explicitly, by name, for every call site — not just the one the agent points to.

Then show a normal (non-blocked) cycle in the same session that DOES write a row, to prove the gate is discriminating and not just always-blocking or always-passing.

**Rejection criteria:** If any call site bypasses the check, or if the live test isn't run, Claim A is rejected regardless of the line citation.

### Claim B — G5 enforcement is hardcoded ENFORCE, and G0–G6 have real ENFORCE paths
**Agent's claim:** Line 3327 in `aiem_diagram3_governance.py` hardcodes G5 to ENFORCE mode; G0–G6 all have working ENFORCE code paths, just currently running in SHADOW.

**Required proof:**
- `sha256sum` of `aiem_diagram3_governance.py`.
- `sed -n` output of lines 3300–3350.
- For **each** of G0 through G6: grep for the literal branch that reads the mode flag and behaves differently in ENFORCE vs SHADOW, e.g.:
  ```
  grep -n "ENFORCE\|SHADOW" aiem_diagram3_governance.py
  ```
  For each hit, show what the ENFORCE branch actually *does differently* from the SHADOW branch — not just that the string exists. A flag that's checked but has an empty or no-op ENFORCE branch is not real enforcement.
- A live test: flip one gate (e.g. G0) from SHADOW to ENFORCE in a test/staging run only, force a fail condition, and show it actually blocks — versus the same fail condition in SHADOW mode, which should log but not block. Two runs, side by side, same condition, different outcome. That difference is the proof.

**Rejection criteria:** A flag existing without a demonstrated behavioral difference between modes is rejected as enforcement, even if the string "ENFORCE" appears in the code.

### Claim C — `enforcement_status = "ENFORCED"` at 25+ locations, contract note is stale

**Rejection criteria:** If `enforcement_status = "ENFORCED"` exists only as a write with no consuming read that alters control flow, this claim is rejected — the status value is decorative, not enforcement.
