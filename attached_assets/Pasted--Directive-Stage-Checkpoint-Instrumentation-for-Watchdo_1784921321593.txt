# Directive — Stage-Checkpoint Instrumentation for Watchdog → Trade Pipeline (2026-07-25)
## SCOPE: Options Engine only. Read alongside Directive_PI8_LiveWatchdogProof_TradeConfirmation_2026-07-25.md.

## Why this exists
Every prior investigation into this pipeline has required after-the-fact log archaeology to guess where it broke. This directive requires the agent to instrument every stage boundary so that the NEXT failure — if there is one — self-localizes to a single stage, with no reasoning or reconstruction required.

This does NOT guarantee catching every possible failure (e.g. infra-level process death, as already happened once with the Replit restart gap). It guarantees that any failure the *application code* passes through will leave a durable, atomic trace of the last stage reached.

## Required stages (one checkpoint row per stage, per trace_id)
1. `WATCHDOG_POLL` — watchdog wakes, before calling `/run-scan`
2. `RUN_SCAN_CALLED` — HTTP call made, before response received
3. `RUN_SCAN_RESPONSE` — response received (status code + body hash), before any gate logic runs
4. `TRIGGER_EVALUATED` — gate decision made (accepted/blocked + reason), before write to `aiem_scan_trigger_log`
5. `TRIGGER_LOGGED` — confirmed write to `aiem_scan_trigger_log` succeeded
6. `SCAN_RUN_CREATED` — row written to `morning_scan_runs`, before pipeline worker picks it up
7. `SEED_STAGE` — `seed_daily_candidates()` entry/exit, candidate count
8. `P2_INIT` — existing checkpoint, unchanged
9. `P2_GATE` — existing checkpoint, unchanged
10. `P2_CAPTURE` — existing checkpoint, unchanged
11. `DECISION_WRITTEN` — confirmed write to `oe_decision_audit` (and `oe_shadow_positions` if applicable)

## Hard requirements (non-negotiable, this is what makes it strict)
- **Write-before-work, not write-after-success.** Each checkpoint must be written the instant that stage is *entered*, before any logic in that stage executes — not after it completes. A stage that crashes mid-execution must still show up as "entered, never exited" rather than vanishing entirely.
- **Atomic, durable writes.** Checkpoint writes must be their own committed DB transaction (or fsynced log line) — not batched with the stage's other work, so a crash inside the stage can't also wipe out the checkpoint for that stage.
- **Every checkpoint carries the same `trace_id`** end-to-end so a single query can reconstruct the full path for one poll cycle.
- **Negative-control test required**: agent must deliberately force a failure inside each of the 11 stages (in a test/dry-run context, not production) and prove the checkpoint for that stage still gets written even though the stage itself fails. A checkpoint scheme that only works when nothing goes wrong is worthless — this is the same principle as the mutation-check rule already standing for quant work.
- **No silent catch-and-continue.** If a checkpoint write itself fails, that must raise/alert, not be swallowed — otherwise the instrumentation becomes the next silent failure mode.
- **Idempotent by trace_id.** Retries/replays must not create duplicate or contradictory checkpoint rows for the same trace_id + stage.
