# Directive — External Infra Monitoring (Heartbeat, Auto-Restart, Missed-Ping Alerting) (2026-07-25)
## SCOPE: Options Engine + underlying aiem-process. Separate work item from stage-checkpoint instrumentation and PI-8 proof. Addresses infra-level failures (process death, restart failure) that application-level logging cannot detect from the inside.

## Why this exists
The 2026-07-24 3:05-8:57 AM EDT gap was an infra failure (process self-exit, platform did not restart it) — not something app-level logs can catch, since a dead process can't log its own death. This directive requires monitoring that lives OUTSIDE the app itself.

## Required components

### 1. External heartbeat monitor
- A `/health` endpoint on aiem-process, separate from `/run-scan`, returning 200 + uptime seconds + last-checkpoint timestamp
- Pinged every 1-2 min by something OUTSIDE Replit (GH Actions cron, Healthchecks.io/UptimeRobot, or an equivalent independent process)
- Must be architecturally decoupled from the watchdog/trigger logic — this checks liveness only, nothing else

### 2. Missed-ping alerting
- If N consecutive pings are missed (agent to propose N with reasoning — e.g. 3 misses = process likely down vs. transient network blip), fire an immediate alert (Telegram/SMS/email) to Joel
- Alert must fire at the time of the miss, not be discoverable only via later log review
- Test required: agent must simulate a missed-ping scenario and prove the alert actually fires

### 3. Process supervisor with auto-restart
- A supervisor (independent of Replit's own platform-level restart behavior, since that's what failed) that detects process exit and relaunches immediately
- Must cover both crash-exit and the previously-existing self-exit pattern (already removed per 2026-07-24 work, but supervisor should be defense-in-depth regardless of app-level behavior)
- Test required: agent must kill the process manually in a test context and prove the supervisor restarts it, with timestamp showing restart latency

### 4. Synthetic heartbeat trail during the risk window
- Scheduled ping every 5 min from 6:50-10:00 AM ET specifically logging "process alive, uptime = X" independent of whether any trigger/trade occurred that cycle
- Purpose: produce a continuous alive/dead trail across the whole window so a gap shows exactly when the process went dark, rather than inferring it from absence of trigger activity
- This is a logging requirement in addition to items 1-3, not a replacement
