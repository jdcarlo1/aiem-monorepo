# Directive 5 — Contamination Forensics + Real Test-Mode Isolation Spec

## Context (why this directive exists)
The prior task (Directive 4 / negative-control test) was executed without a
real spec file — `D3_directive4_test_mode_isolation.md` does not exist and
never has (confirmed: zero filesystem hits, zero git history, no transcript
content beyond the filename being referenced). In its absence, the agent
improvised a monkey-patch of `_g0_read_config` instead of stopping and
reporting the missing spec as blocking.

That monkey-patch only intercepted a config **read**. It did not intercept
DB **writes**. As a result, `require_governance_authorization` was called
with `is_test_record=False` (the hardcoded production value in
`_aiem_paper_execute_today`), and the test run **wrote 3 permanent rows**
to production governance tables:
- `d3_governance_requests`
- `d3_governance_event_links`
- `d3_governance_decisions`

All three rows are flagged `is_test_record=FALSE` even though they
originated from a forced/fabricated test scenario, and are immutable by
trigger.

This directive has two parts. Do not skip either. Do not combine or
shortcut the steps below.

## PART B — Real test-mode isolation spec (before any future negative-control test is attempted)

Goal: define an isolation mechanism that actually satisfies "would have
halted the paper Decision Engine without touching live trading or
production audit tables" — and that intercepts writes, not just reads.

Choose **one** of the two mechanisms below. Do not invent a third
(e.g. another monkey-patch) without stopping to get approval first.

**Option 1 — Transactional rollback around the full test invocation**
- Wrap the entire `_aiem_paper_execute_today()` test invocation in a
  single DB transaction (`BEGIN` before, `ROLLBACK` after — not commit).
- This must cover every write path touched during the run, including
  `d3_governance_requests`, `d3_governance_event_links`,
  `d3_governance_decisions`, and any other table the call chain touches
  — not just the one function that was patched last time.
- Prove coverage: paste the query used to confirm zero rows exist
  post-rollback in all affected tables, run immediately after the
  rollback.

**Option 2 — Duplicate/isolated test database**
- Point the test run's DB connection at a separate schema or database
  instance so all writes land there, not in production tables.
- Prove isolation: paste connection-string/config diff showing the test
  run's target differs from production, and paste a query against the
  *production* tables immediately after the test run showing zero new
  rows.

For whichever option you choose, before running the actual
negative-control test, produce and paste:
- The exact code change implementing the isolation (diff + sha256
  before/after).
- A dry run showing the isolation mechanism actually intercepts a write
  (not just a read) — e.g. attempt a write inside the isolated context,
  then prove it either rolled back or landed in the separate target.

Only after that proof is provided should the actual negative-control
test (forcing a BLOCK verdict and tracing it through D1→D2→Decision
Engine) be attempted.
