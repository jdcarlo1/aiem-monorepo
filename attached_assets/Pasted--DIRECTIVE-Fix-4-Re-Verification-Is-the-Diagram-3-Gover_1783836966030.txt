# DIRECTIVE — Fix 4 Re-Verification: Is the Diagram 3 Governance Layer Actually Receiving Data?

## Context — do not skip

The documented architecture is:

- **Diagram 3** (Governance/Executive Layer) governs Diagram 1. It receives system health, audit, learning, and performance information **after processing**, and issues governance decisions (approve, pause, quarantine, rollback) back to Diagram 1.
- **Diagram 1** (Master Orchestrator) is the only orchestrator that starts, schedules, and coordinates the trading pipeline. It carries out Diagram 3's decisions.
- **Diagram 2** (Trading & Analysis Pipeline) runs independently under Diagram 1's coordination.
- Diagram 3 does **not** reach into Diagram 2 directly, and does **not** bypass Diagram 1. This separation is intentional.

This is the correct target architecture. The question is **not** whether `_h_specialist_council()` / `run_full_cycle()` should be merged into the live `run_council()` production path — they should NOT be, by design. The question is whether the Diagram 3 governance layer is actually functioning at all, given that its only known code path (`run_full_cycle()` → `_h_specialist_council()`) was found to have **zero call sites in main.py**.

If Diagram 3 is supposed to receive real post-processing data and issue real governance decisions, but its only entry point is never invoked, then **the governance layer is inert** — not "intentionally separated," but non-functional. That is a different and more serious finding than what was previously accepted.
