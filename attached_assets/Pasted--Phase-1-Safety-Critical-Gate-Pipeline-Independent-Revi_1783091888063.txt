## 🔴 Open Item 1 — Kill Switch Not in the Structural Gate Chain

**Claim in report:** "WIRED (via AIEM tool, instruction-gated)"

**What's actually true:** `premarket_open_trader.evaluate_ticker()` runs 6 hard gates. None of them is `kill_switch`. The only way `kill_switch` gets checked during the premarket flow is indirectly, via `pre_decision_risk_gate.py:224` calling `kill_switch._is_currently_halted()` internally — but `pre_decision_risk_gate` is itself only invoked if the AIEM agent chooses to call that tool. The standalone `check_kill_switch` tool is instruction-gated only (`main.py:30867` system prompt tells the agent to call it — nothing in code forces it).

**Why this matters:** A ticker can pass all 6 hard gates and get a paper pick written at 9:52 AM without kill_switch ever being consulted, if the AIEM agent isn't running or skips the tool call at that moment.

**What to ask for:**
1. Confirm whether `pre_decision_risk_gate` (and therefore the internal kill_switch check) is unconditionally called somewhere in the premarket execution path, or only on agent discretion. If only on discretion, that's the actual gap.
2. If it's discretion-only, request kill_switch be added as a **7th hard gate** directly inside `evaluate_ticker()`, structurally — same pattern as `daily_loss_limit` or `earnings_calendar` — so it can't be skipped regardless of what the AIEM agent does.
3. Ask for a repeat of the isolated gate-block test but run *through the actual premarket execution path* (not a hand-constructed `check_kill_switch(...)` call) to prove reachability, not just correctness in isolation.

## 🔴 Open Item 2 — Risk Gate Hard-Block May Depend on LLM Availability

**Claim in report:** "WIRED — INTEGRATED WITH GAPS"

**What's actually true:** Test case WR=30%, n=10, conviction=0.2 — a deliberately weak signal — returned `APPROVED_WITH_CAUTION`, not `BLOCKED`, when run with no `ANTHROPIC_API_KEY` set (rule-based layers only). The devil's-advocate LLM pass was unavailable in that test.

**Why this matters:** If the LLM pass is what actually produces hard blocks, then losing the API key in production silently downgrades this gate from a hard block to advisory-only — with no visible failure, no alert, just weaker gating.

**What to ask for:**
1. Re-run the identical test (WR=30%, n=10, conviction=0.2) **with a valid `ANTHROPIC_API_KEY` set**, to see if the LLM pass produces `BLOCKED` where the rule-based-only path produced `APPROVED_WITH_CAUTION`.
2. If yes — confirm explicitly whether rule-based thresholds alone are intended to ever hard-block anything, or whether the LLM pass is a hard dependency for blocking. If it's a hard dependency, request either (a) rule-based thresholds tightened so a weak-enough signal blocks without the LLM, or (b) the system fails safe (blocks, not just cautions) when the API key is missing, rather than silently degrading.
3. Ask for a log/alert to be added for "devil's advocate pass unavailable" events, so this degradation isn't invisible if it happens live.
